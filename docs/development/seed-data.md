# Development seed data

> **SYNTHETIC / DEVELOPMENT ONLY / NEVER PRODUCTION.** Everything on this page exists only inside the disposable
> test-classpath launcher described in [local runtime](local-runtime.md). No migration, production configuration,
> profile or deployment can create or enable it.

## Start and inspect

```powershell
.\mvnw.cmd -B spring-boot:test-run "-Dspring-boot.run.main-class=io.github.piresrenan.orderhub.development.LocalDevelopmentApplication"
```

The launcher starts a new PostgreSQL Testcontainer, the application on `127.0.0.1:8080` and a separate
loopback-only synthetic issuer on `127.0.0.1:9090`. It then applies the seed below through the real application use
cases. The issuer answers `/fixture` and `/tokens/{persona}` only after the whole seed succeeded; a failed step aborts
startup and nothing partial is published. Ctrl+C stops everything and discards the database. To reset, stop and start
the launcher again: the same logical scenario is rebuilt. Do not edit the database by hand.

```powershell
$fixture = Invoke-RestMethod http://127.0.0.1:9090/fixture
function Get-DevToken($persona) {
    (Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:9090/tokens/$persona" -ContentType application/json).access_token
}
function Get-TenantId($key) { ($fixture.tenants | Where-Object key -eq $key).id }
```

Tokens are short-lived (five minutes), signed by the disposable issuer on demand and never written anywhere. Request a
new one when it expires. Swagger UI for the running instance is at `http://127.0.0.1:8080/swagger-ui/index.html`.

## Manifest fields

`GET /fixture` returns synthetic, non-secret selectors in this order:

- `schemaVersion`: manifest format version (currently 1).
- `issuer`: the loopback issuer base URI.
- `tenantId`, `productId`, `variantId`, `customerId`: compatibility selectors for Tenant alpha, its notebook product,
  its `LOCAL-NOTEBOOK` variant and its first Customer (used by the examples in [local runtime](local-runtime.md)).
- `personas`: `name`, `subject`, `userId` (null for `unbound`), `description`, `tenantAccess` (Tenant key to
  `STAFF_GOVERNANCE`, `STAFF_NO_ROLE`, `STAFF_SUSPENDED`, `STAFF_TERMINATED`, `CUSTOMER` or `UNBOUND`),
  `platformPermissions`, `organizationPermissions`.
- `organizations`: `key`, `id`, `name`, `status`, `tenants`.
- `tenants`: `key`, `id`, `name`, `status`, `organization`, `inventoryPolicy`, `governanceStaff`,
  `governanceRoleCode`, `staffPlacement` (`departmentId`/`positionId` needed for Staff provisioning; null without Staff).
- `customers`: `key`, `tenant`, `customerId`, `linkedPersona`.
- `catalog`: per Tenant key, `categories`, `products` and `variants` (with `sku`, `status` and `prices`).
- `inventory`: per Tenant key, positions with `onHand`, `committed`, `backordered` and `safetyStock` at seed time.
- `orders`: `key`, `tenant`, `persona`, `customer`, `orderId`, `idempotencyKey`, `items`, `allocation`.
- `outstanding`: an unconsumed Customer account-link proof and an unconsumed Staff provisioning intent (identifiers
  only; their one-time credentials are never published).

The manifest never contains bearer tokens, proof credentials, private keys or database passwords. Catalog, Customer
and operation identifiers are deterministic across restarts; Organization, Tenant, User, Order, proof and intent
identifiers are generated by the product, so always read them from `/fixture`.

## Personas

Every token subject is `synthetic-local-<persona>`. Authority comes only from real grants, memberships, roles and
Customer links created by the seed, never from token claims.

| Persona | Authority | Valid Tenants | Denied Tenants (expected) | Token |
| --- | --- | --- | --- | --- |
| `platform` | Platform grants: organizations view/manage, tenants manage, organization grants manage | none (Platform administration only) | all Tenant business routes: 403 | `Get-DevToken platform` |
| `staff` | Governance Staff (`INITIAL_TENANT_GOVERNANCE_V1`) | alpha | beta, gamma, delta, epsilon: 403 | `Get-DevToken staff` |
| `beta-admin` | Governance Staff | beta | others: 403 | `Get-DevToken beta-admin` |
| `multi-tenant-staff` | Governance Staff in two Tenants | alpha, gamma | beta, delta, epsilon: 403 | `Get-DevToken multi-tenant-staff` |
| `alpha-member-no-role` | Active Staff membership without a role | none (membership only) | alpha and others: 403 | `Get-DevToken alpha-member-no-role` |
| `alpha-suspended` | Alpha Staff with SUSPENDED membership | none | alpha and others: 403 | `Get-DevToken alpha-suspended` |
| `alpha-terminated` | Alpha Staff with TERMINATED membership | none | alpha and others: 403 | `Get-DevToken alpha-terminated` |
| `org-viewer` | `ORGANIZATION_TENANTS_VIEW` on organization north | lists north's Tenants | south: 404 (anti-enumeration); Tenant business: 403 | `Get-DevToken org-viewer` |
| `customer` | Customer linked in two Tenants | alpha, beta (own Orders) | Staff administration: 403 | `Get-DevToken customer` |
| `alpha-customer-2` | Second alpha Customer | alpha (own Orders) | the other alpha Customer's Orders: 404 | `Get-DevToken alpha-customer-2` |
| `beta-customer` | Customer linked only in beta | beta (own Orders) | alpha: 403 | `Get-DevToken beta-customer` |
| `outsider` | Bound User with no membership or grant | none | all: 403 | `Get-DevToken outsider` |
| `unbound` | Verified local identity never bound to a User | bootstrap routes only | all business routes: 401 | `Get-DevToken unbound` |

A completely unknown identity (foreign issuer or invalid signature) cannot be issued by the local issuer; any other
token is rejected with 401.

v1 can create exactly one Staff role, `INITIAL_TENANT_GOVERNANCE_V1`, through the initial-Staff ceremony, and normal
provisioning either assigns that role or no role. A partially privileged "operational" Staff persona therefore does
not exist in v1 and is deliberately not faked.

| --- | --- | --- | --- |
| alpha | north | ACTIVE | policy DENY; governance `staff` and `multi-tenant-staff`; richest data |
| beta | north | ACTIVE | policy ALLOW_BACKORDER; governance `beta-admin` |

## Catalog

alpha and beta each contain the same catalog with the same slugs and SKUs but different identifiers (uniqueness is
Tenant-scoped), so any cross-Tenant leak is visible. gamma contains only `PAPER-A4` under `office`.

- Categories: `office` > `office-paper` > `office-paper-premium`, and `electronics`.
- Products: `synthetic-notebook`, `paper-ream`, `premium-pen` (ACTIVE; `premium-pen` has no brand or description),
  `standing-desk` (DRAFT), `desk-lamp` (ARCHIVED).
- Variants: `LOCAL-NOTEBOOK`, `PAPER-A4` (BRL and USD prices, attributes, MPN), `PAPER-LETTER`, `PEN-BLUE` (ACTIVE);
  `PAPER-A3` (INACTIVE); `PAPER-A5`, `DESK-STD` (DRAFT, no price); `LAMP-OLD` (ARCHIVED).

## Inventory

At seed time: alpha `LOCAL-NOTEBOOK` 100 on hand; `PAPER-A4` 48 on hand (receipt 50, damaged adjustment -2), safety
stock 5, 3 committed; `PAPER-LETTER` 20 on hand, 2 committed; `PEN-BLUE` 0 on hand (receipt then stock-count
adjustment). beta `PAPER-A4` 5 on hand, 5 committed, 3 backordered; `PEN-BLUE` 0 on hand, 1 backordered. gamma
`PAPER-A4` 10 on hand. Every movement has receipt/adjustment history visible at `/inventory/positions/{variantId}/movements`.

## Customers and Orders

Customers: alpha `alpha-linked` (`customer`), `alpha-second` (`alpha-customer-2`), `alpha-unlinked` (has the
outstanding link proof); beta `beta-linked-shared` (`customer`), `beta-linked` (`beta-customer`); gamma
`gamma-unlinked`. CustomerProfile rows are the one fixture-only write, because v1 has no Customer creation command;
every link then uses the real proof issuance and consumption.

Orders (all status CREATED): `alpha-single-item` (FULLY_ALLOCATED), `alpha-multi-item` (FULLY_ALLOCATED, two items),
`beta-partial-backorder` (PARTIALLY_BACKORDERED), `beta-full-backorder` (FULLY_BACKORDERED). Each was created through
the Customer Order use case with the idempotency key `seed-<order key>`; replaying that key with the same body over HTTP
returns the same Order.

## Journeys

```powershell
$alpha = Get-TenantId alpha; $beta = Get-TenantId beta
$staff = @{ Authorization = "Bearer $(Get-DevToken staff)"; 'X-Tenant-Id' = $alpha }
$a4 = ($fixture.catalog.alpha.variants | Where-Object sku -eq 'PAPER-A4').id

# Catalog and inventory (200)
Invoke-RestMethod -Uri http://127.0.0.1:8080/catalog/products -Headers $staff
Invoke-RestMethod -Uri "http://127.0.0.1:8080/inventory/positions/$a4" -Headers $staff

# Replay a seeded Order (201, same Order as the manifest)
$customer = @{ Authorization = "Bearer $(Get-DevToken customer)"; 'X-Tenant-Id' = $alpha
               'Idempotency-Key' = 'seed-alpha-single-item' }
$body = @{ customerId = $fixture.customerId; items = @(@{ variantId = $a4; quantity = 2 }) } | ConvertTo-Json -Depth 4
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/orders -Headers $customer -ContentType application/json -Body $body

# Cross-Tenant denial: alpha Staff selecting beta (403)
Invoke-WebRequest -SkipHttpErrorCheck -Uri http://127.0.0.1:8080/catalog/products `
    -Headers @{ Authorization = "Bearer $(Get-DevToken staff)"; 'X-Tenant-Id' = $beta }

# Suspended membership (403) and unbound identity (401)
Invoke-WebRequest -SkipHttpErrorCheck -Uri http://127.0.0.1:8080/catalog/products `
    -Headers @{ Authorization = "Bearer $(Get-DevToken alpha-suspended)"; 'X-Tenant-Id' = $alpha }
Invoke-WebRequest -SkipHttpErrorCheck -Uri http://127.0.0.1:8080/catalog/products `
    -Headers @{ Authorization = "Bearer $(Get-DevToken unbound)"; 'X-Tenant-Id' = $alpha }

# Platform administration (200)
Invoke-RestMethod -Uri http://127.0.0.1:8080/platform/organizations -Headers @{ Authorization = "Bearer $(Get-DevToken platform)" }
```

| Journey | Persona | Tenant | Expected |
| --- | --- | --- | --- |
| `catalogProducts`, `inventoryGetPosition` | `staff` | alpha | 200 |
| `ordersCreate` replaying `seed-alpha-single-item` | `customer` | alpha | 201, same Order |
| `ordersCreate` new key, `PEN-BLUE` quantity 1 | `customer` | alpha | 409 (DENY policy, no stock) |
| `ordersCreate` new key, `PEN-BLUE` quantity 1 | `beta-customer` | beta | 201, FULLY_BACKORDERED |
| `ordersView` of another Customer's Order | `alpha-customer-2` | alpha | 404 |
| `catalogProducts` | `staff` | beta | 403 |
| `catalogProducts` | `alpha-suspended`, `alpha-terminated`, `alpha-member-no-role`, `outsider`, `platform` | alpha | 403 |
| `catalogProducts` | `unbound` | alpha | 401 |
| `organizationListTenants` for north / south | `org-viewer` | none | 200 / 404 |
| `identityIssueInitialStaffProvisioning` then `identityBootstrapStaff` | `platform`, then `unbound` | epsilon | 200, 200 (the `unbound` identity becomes epsilon's first Staff) |
| `identityIssueStaffProvisioning` with `tenants[alpha].staffPlacement` | `staff` | alpha | 200 |

Direct database access by the seed is an internal fixture detail (CustomerProfile rows and a Staff placement read). It
is not a public workflow; use the API.
